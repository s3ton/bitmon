# bitmon

**bitmon** is a **smartphone-first, portrait-only, installable PWA** creature-collection RPG set on a 1:1 representation of Earth, rendered as an original **low-poly 2.5D** world.

The geographic base uses **OpenFreeMap as the sole geographic data source** and **MapLibre for rendering**. No physical building or road may be generated unless it exists in the OpenFreeMap tiles. Original window, roof, and facade art may be inferred from those tiles but does not claim to reproduce actual architecture. The game adds original facade and roof treatments on mapped buildings, plus characters and creatures. **Immediate development focus:** touch-controlled walking-avatar exploration with a normally 45° zoomable camera that gently recenters after sustained movement and tilts toward overhead only when real mapped buildings obscure the avatar. **Later battles** zoom/reframe in the same low-poly world, then restore and resume heading-following exploration. Progression is local-first and verifiable with permissionless trainer registration, public randomness, restricted creature swaps, and player-led gyms.

## Toolchain

Use **Node.js 26 LTS** (root `.nvmrc`, package engine, and GitHub Actions). Direct packages are exact-pinned: MapLibre GL JS 6.16.0, Vite 8.3.5 and TypeScript 7.0.2. PR #26 adds `package-lock.json` (npm lockfile v3) and switches both CI jobs to `npm ci` for reproducible transitive dependencies. **The Pages workflow executes from `main`**, so its `npm ci` change only takes effect after an explicitly approved promotion to `main`.

## Local build

```sh
nvm use
npm ci
npm run build
npm run dev
```

The build runs TypeScript validation once, compiles Vite assets and stamps `dist/sw.js` with a digest of the compiled app shell so changed builds are detectable. Run `npm run check` separately when you only want TypeScript validation without a build; CI uses `npm run build` to avoid redundant checks.

**Player settings:** Camera responsiveness and zoom are restored after restarting the PWA. Future real preferences should be implemented using a native input, select or textarea marked `data-setting="unique-name"`; `src/settings.ts` then saves/restores all marked controls into one channel-prefixed JSON record. Initialize them before reading initial map/game state. Do not mark transient controls such as the coordinate teleport field. Stable and Preview settings remain separate.

**Preview startup collision recovery:** Following an installed-PWA update, a device report showed movement stuck on "Map data is not loaded here." A focused fix restores initialization when the map finishes loading: the normal decoded-tile events remain authoritative where available, while a fallback requires a PBF that the app actually supplied to MapLibre plus a settled source/viewport. Failed or unknown tile requests remain blocked. The prior misplaced fallback in teleport rollback was removed. Reopen installed Preview after deployment to verify walking and offline boundaries on the phone; CI does not establish device acceptance.

**Cache and collision review:** One in-flight PBF request is shared per tile key; downloaded binary bytes are queued for persistence without making map rendering wait for disk writes. Metadata holds only tile key and byte size; exact duplicate polygons with the same height are ignored, while differently-heighted overlapping buildings remain available for camera occlusion. A separate downloaded-tile tracking set was removed. All player-foot samples must belong to decoded source tiles before their geometry can authorize walking into them. Missing distant viewport tiles do not invalidate already-verified nearby collision data. The app shell uses cache-first for cached static assets and network-first navigation.

**Preview map storage:** When deployed, the exploration PWA keeps only the OpenFreeMap vector tiles that are actually requested while viewing and walking, or explicitly jumping to coordinates. MapLibre reads and writes them through IndexedDB (not a speculative planet download). The storage target is **100 MiB of tile bytes per channel**; when full, farthest-from-player cached tiles are deleted to make room, while the player's current tile is protected. The live map and settings indicator show how much is used. The saved player coordinate uses a channel-specific localStorage key. Neither location nor map tiles are sent to a bitmon server; online loading still contacts OpenFreeMap. [Persistent storage enhancement PR #29](https://github.com/s3ton/bitmon/pull/29) adds a protection request. On standalone installed-app launches, bitmon checks `navigator.storage.persisted()` and asks for `navigator.storage.persist()` if needed. Settings displays whether the device accepted storage protection and offers a retry if denied. Ordinary browser tabs do not request persistent storage. Even when granted, users can still clear the saved app/site data. **Web storage permissions are origin-wide**, not unique to the installed PWA: Stable and Preview share an origin-level permission/quota (and potentially other pages on that origin), while keeping their existing map databases and player saves separate.

## Two GitHub Pages PWAs — phone testing and stable releases

1. Keep [Settings → Pages](https://github.com/s3ton/bitmon/settings/pages) set to **GitHub Actions** with `github-pages` environment deployments restricted to `main`. The independent Preview/Stable publishing infrastructure has already been bootstrapped on `main`.
2. After deployment, open and install **[bitmon Preview](https://s3ton.github.io/bitmon/preview/)** to test the latest reviewed `preview` branch. It should have a **purple Preview icon and "bitmon DEV" home-screen label**, distinct from the teal Stable app. A successful `preview` push CI automatically republishes Preview without a gameplay merge to `main`. The root [bitmon Stable](https://s3ton.github.io/bitmon/) remains compiled only from `main`.
3. On a portrait phone, verify Preview offers a **separate installation**, with its purple icon and distinct name, while Stable remains installed. Also open installed Preview from its home-screen icon and check Settings → storage protection: it should be granted, denied/best-effort, or explicitly unsupported. An ordinary browser tab must not request it. Close/reopen the app and restart the phone to verify cached PBF tiles and the saved player position survive; user-deleted site data remains an exception. Then change camera responsiveness and zoom, close/reopen installed Preview, and verify both settings are restored without affecting Stable. Then check joystick up/down direction, short sidesteps/backward walks without sudden camera flips, source-driven automatic overhead tilt instead of through-wall avatar rendering, the top-right hamburger menu with camera presets (close it by choosing a preset), 10 m/s diagonals, 15.5–20 right-side zoom slider, scale-adjusting trainer, collision, offline shell and both home-screen launches. For the new prototype: enter coordinates such as `45.4715, 9.1869` (latitude first), confirm an online jump to walkable land and invalid/unavailable destination rejection, walk around to save tiles, reload to restore position, then switch offline and verify movement stops at the edge of uncached geography. Verify changing preview leaves Stable unchanged.
4. [Release PR #11](https://github.com/s3ton/bitmon/pull/11) and [release PR #25](https://github.com/s3ton/bitmon/pull/25) have been merged. Future changes to Stable still require a separate, explicitly approved `preview` → `main` release PR.

On a device running a previously installed version, a new service worker waits until the user taps **Reload** in the update notice; a new build does not forcibly reload an active session. After PR #26 reaches Preview, test this by deploying a subsequent changed Preview build, reopening/foregrounding the installed app, and verifying that the prompt appears and reloads only on request. Check offline reopening of the cached shell and confirm Stable's cache is unchanged. Both PWAs require internet for uncached OpenFreeMap tiles; previously visited vector tiles can be used offline after the new feature is deployed. No game progress is saved yet; future localStorage or IndexedDB keys must be namespaced by channel because browser storage is origin-wide.

These are working design documents, not a completed game or security audit.
